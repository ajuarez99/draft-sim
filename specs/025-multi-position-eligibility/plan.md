# Implementation Plan: Multi-position eligibility for basketball players

**Branch**: `025-multi-position-eligibility` | **Date**: 2026-10-09 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/025-multi-position-eligibility/spec.md`, clarified: FR-002 = C (no primary on labels; simulation unchanged), FR-004 = A (count fully in every eligible position).

## Summary

**The data.** Every `PlayerRef` on the wire gains `positions`, the player's full eligible list. This is an additive change to one record with two construction sites, with no migration and no engine change.

**The client rule.** One frontend helper, `eligiblePositions(p)`, becomes the only way the draft rooms read a player's positions. Built on it:

- **Labels** show "PG/SG" in basketball order, with a split-colour pill and no rank number for multi-position players.
- **Filters, scarcity and pick runs** count by eligibility.
- **"Your team" and "fills a need"** use a TypeScript port of the backend's proven seating method (best players first, reshuffling between slots so one more fits), replacing the frontend's two-pass greedy.

**The pin.** A parity fixture ties the TypeScript seating to `BasketballRules`. A backend test generates the fixture from `BasketballRules` and fails if the committed file is stale. A vitest test runs the TypeScript port over the same cases, so the two cannot quietly drift apart.

- Plus scarcity.ts, pickRun.ts, teamNeeds.ts and posRank.ts.

## Build order

1. Wire field, Java + `api.ts`, and the `eligiblePositions`/`positionLabel` helpers.
2. The parity fixture generator (backend), then `lineup.ts` plus its parity test. **Prove each test can fail.**
3. Rewire `teamNeeds.ts` to `lineup.ts` for NBA, and change `openSlotFor`/`fitSlot` to take the player.
4. Scarcity, pick runs and filters.
5. Labels and pills, with posRank's no-rank rule.
6. Live verification per quickstart, then the bug-hunt review.

The repo pipeline applies: an adversarial plan review **before** code, a Sonnet build, a review, then live verification.

## Amended after plan review (2026-10-09)

[plan-review.md](plan-review.md) found **1 blocker and 10 should-fixes**. All are resolved in research.md §Amendments A1–A10 and in the amended tasks. The user decided two of them:

- **Family runs** (Guard / Forward / Center), measured at 26 of 163 windows with 0 ties.
- **Family codes in compact cells** ("G", "F", "G/F", "F/C").

The rest:

- **Blocker fixed:** "Fills X" names a directly eligible open slot, never a filled one (A1). The review measured the original rule naming a filled slot in 64% of joinable checks.
- **Ranks:** no rank on any NBA badge (A3).
- **Parity fixture:** built only through `BasketballRules`' public API (A4), and compared as parsed JSON (A5).
- **Fit function:** a `fitFor(player)` prop replaces `openSlots` (A6).
- **Colour:** colour never singles out one position (A7).
- **Scope:** `CompletedDraftBoard` changes too, and that is in scope (A8).
- **Baseline:** SC-001's baseline is corrected to 4 of 5 chips today, with expected eligible counts PG 38 · SG 41 · SF 37 · PF 45 · C 31 (A10).
- **New task T002b:** captures the SC-004 replay baseline before any code.

## Risks for the adversarial review (answered; see plan-review.md)

- **Template mismatch.** The backend template is **hardcoded** to the nine-slot NBA shape, while the frontend reads `rosterPositions`. Parity is only proven on that shape. Does any league in the DB use a different NBA shape? *[measured]* All four NBA leagues in the local DB use exactly `PG,SG,G,SF,PF,F,C,UTIL,UTIL` + 5 BN: Ball Knowers 2024, 2025 and 2026, and Test 2026. Parity on that shape covers every real league today. Other shapes fall back to the generalized TS seating, which is unpinned, and that is stated.
- **Tie-breaking.** Is ADP ascending exactly the backend's value order, including ties (`exp(-adp/decay)`, stable sort)? And is the roster order fed to the TS port the same as `RosterState.picks()`?
- **Which slot the label names.** When a candidate can only be seated by augmentation, which slot does "Fills X" name? Could it name a slot he isn't directly eligible for, which would confuse the user?
- **Stale fixture failure.** The backend test reading and writing a file under `web/` couples the two builds. Is that acceptable for CI, given the backend deploys separately?
- **Pill fit.** A three-position pill in compact cells, measured not assumed.
- **Hidden single-position assumptions.** `onBrand.ts`/`pickInsight.ts` may group or compare by `.position` in ways the list above misses.
